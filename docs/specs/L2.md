# L2 - Detailed Requirements

**Status:** Detailed baseline derived from the user-confirmed L1 scope; source review does not certify runtime conformance.
**Baseline:** Repository commit `6fdc7bd448`, inspected on 2026-10-03.

## Interpretation and coverage

This document elaborates all 16 [L1 requirements](L1.md). Each L2 traces to exactly one L1. Observed behavior has source or test evidence; prescribed behavior follows AGENTS.md; proposed detailed contracts elaborate the confirmed cross-cutting intent and require future acceptance validation. These categories describe provenance, not pass/fail status.

Coverage is repository-level with concrete behavior for representative Button, Input, FluentProvider, Web Component Button, DonutChart, ResponsiveContainer, and bundle isolation fixtures. Other component families require their own interaction and data requirements before implementation changes; this document does not claim exhaustive catalog coverage. Acceptance scenarios referring to test data use the fixture defined in the cited evidence. Review criteria are verified by source or document inspection; interaction criteria require an executable acceptance test.

No authentication service, persistence backend, or uniform application breakpoint layout is introduced. Host navigation, resource loading, and configured forms remain explicit consumer operations. Numeric performance budgets and minimum browser release versions are unresolved rather than invented.

## L2-001: React Button defaults and activation
**Traces to:** L1-001

Button must provide native button behavior by default and forward consumer activation callbacks.

**Basis:** Observed: E01, E02.

**Acceptance Criteria:**
1. Given a Button with text and no polymorphic override, when it renders, then its root is a button element with type="button", appearance="secondary", shape="rounded", and size="medium" outside a size-providing context.
2. Given an enabled Button with an onClick spy, when the user clicks it once, then the callback is invoked once.
3. Given a Button inside a form without an explicit type, when it is clicked, then it does not submit that form.

## L2-002: Button link polymorphism
**Traces to:** L1-001

Button rendered as an anchor must expose the semantics appropriate to the presence of href.

**Basis:** Observed: E01, E02.

**Acceptance Criteria:**
1. Given Button with as="a" and href="/destination", when it renders, then its root is an anchor with that href and no overriding button role.
2. Given Button with as="a" and no href, when it renders, then its root has role="button" and tabIndex=0.

## L2-003: Input defaults and change notification
**Traces to:** L1-001

Input must initialize its native input slot predictably and notify consumers of changed text.

**Basis:** Observed: E03, E04.

**Acceptance Criteria:**
1. Given Input with neither value nor defaultValue, when it renders, then its native input has type="text" and an empty value.
2. Given an uncontrolled Input with an onChange spy, when a change event supplies the text "alpha", then the rendered value becomes "alpha" and the callback data contains value="alpha".
3. Given an uncontrolled Input containing "alpha", when a change event clears it, then the rendered value and callback data value are the empty string.

## L2-004: Controlled and uncontrolled Input ownership
**Traces to:** L1-002

Input must keep controlled values owned by the consumer and use defaultValue only for initialization.

**Basis:** Observed: E03, E04.

**Acceptance Criteria:**
1. Given Input with value="hello" and defaultValue="world", when it mounts, then its value is "hello".
2. Given Input with value="hello" whose consumer does not update value, when text entry requests "world", then onChange reports "world" and the displayed value remains "hello".
3. Given that controlled Input, when the consumer rerenders it with value="world", then its displayed value becomes "world".
4. Given Input initialized with defaultValue="hello", when the consumer changes only defaultValue to "world", then the displayed value remains "hello".

## L2-005: Optional slots and ref destinations
**Traces to:** L1-002

Button and Input must preserve optional slot content and forward refs to their documented primary elements.

**Basis:** Documented/prescribed: E05; observed: E02, E04.

**Acceptance Criteria:**
1. Given Button with icon content, when it renders, then that content appears in its icon slot; given no icon, when it renders, then no icon slot is instantiated.
2. Given Input with contentBefore="prefix" and contentAfter="suffix", when it renders, then both contents appear outside the native input in their respective slots.
3. Given a ref passed to Button or Input, when the component mounts, then ref.current is respectively the button root or the native input element.

## L2-007: Theme inheritance and overrides
**Traces to:** L1-003

Nested FluentProvider themes must inherit parent values and override explicitly supplied values.

**Basis:** Observed: E07; documented: E06.

**Acceptance Criteria:**
1. Given a parent theme with two distinct token values and a child provider overriding only one, when the child renders, then its effective theme contains the child value for the overridden token and the parent value for the other.
2. Given a nested provider without a theme prop, when it renders, then its effective theme is inherited from its parent.
3. Given a provider whose theme changes from webLightTheme to webDarkTheme, when it rerenders, then its generated theme rule contains the supplied dark theme token values.

## L2-008: Token-based styling and theme variants
**Traces to:** L1-003

New React v9 styling must consume semantic design tokens and support the documented theme objects.

**Basis:** Prescribed/documented: E06, E21.

**Acceptance Criteria:**
1. Given added or modified color, spacing, or typography declarations in v9 component styling, when they are reviewed, then they reference tokens from @fluentui/react-theme rather than hardcoded values.
2. Given the React theme package public API, when webLightTheme, webDarkTheme, teamsLightTheme, teamsDarkTheme, and teamsHighContrastTheme are imported, then each resolves to a theme object.
3. Given Button under each listed theme, when its theme rule is inspected, then its referenced color tokens resolve from that theme rather than a fixed theme-specific literal.

## L2-010: Button disabled and disabled-focusable states
**Traces to:** L1-004

Disabled states must prevent activation while distinguishing removal from the tab sequence from focusable disabled behavior.

**Basis:** Observed: E01.

**Acceptance Criteria:**
1. Given a Button with disabled=true, when the user tabs through the fixture, then focus skips the Button; when the user clicks it, then onClick is not invoked.
2. Given a Button with disabledFocusable=true, when the user tabs through the fixture, then it receives focus; when the user clicks it, then onClick is not invoked.
3. Given an enabled Button between two focusable controls, when the user tabs forward, then the Button is reachable in document order.

## L2-019: Web Component Button form behavior
**Traces to:** L1-007

## L2-030: Bundle isolation verdicts and tracked debt
**Traces to:** L1-011

Bundle isolation must classify clean output, explicitly tracked leaks, and regressions separately.

**Basis:** Documented: E19.

**Acceptance Criteria:**
1. Given an opted-in fixture with no forbidden retained package, when verification completes, then its finding is CLEAN and an otherwise clean run exits 0 with PASS.

4. Given an allowed leak and strict mode, when verification completes, then the run fails.

1. Given a ResponsiveContainer child spy and ResizeObserver entry with width=375.9 and height=200.9, when the animation frame executes, then the child receives width=375 and height=200 and onResize receives the original unrounded dimensions.
2. Given measured width=600, aspect=2, and maxHeight=250, when child dimensions are calculated, then child width is 600 and height is 250.
3. Given identical repeated rounded dimensions, when resize entries arrive, then the size state retains its existing value rather than producing a new dimension state.
4. Given a mounted observer, when ResponsiveContainer unmounts, then the observer disconnects and its tracked pending animation frame is canceled.
5. Given responsive chart fixtures using containers at each width in L2-042, when their observers report the container dimensions, then the child width equals the measured container width rounded down.

## Conformance gaps and unresolved product decisions

- **Execution status:** No runtime acceptance checks were executed. Nx connector tools were unavailable and the earlier Nx CLI attempt could not start because yarn was absent from PATH. Document structure, traceability, and local evidence links are validated separately.
- **Historical deviations:** ResponsiveContainer currently uses React.FC, browser access through a chart utility, and class merging that places library classes after consumer classes. Those patterns do not override AGENTS.md. Its measured sizing behavior is evidence for L2-044; architecture conformance still requires remediation before claiming the prescribed contract is met. The Input implementation also imports react-field, so the existing dependency needs assessment against the prohibition on component package dependencies; it does not authorize adding that pattern.
- **Coverage gaps:** Security instrumentation, the viewport matrix, coexistence fixture, full forced-colors/reduced-motion coverage, and isolated package-consumer scenarios are detailed acceptance targets, not reported passing tests. A supplied L1 confirmation approves scope, not historical conformance.
- **Performance:** Runtime latency, throughput, memory limits, and maximum bundle bytes have no approved numeric budgets in this specification. L2-029 requires measurable reporting and explicit threshold provenance; performance guarantees must be added with evidence or product decisions.
- **Compatibility:** The React peer declaration includes version 16 while the inspected integration matrix explicitly lists 17, 18, and 19. Minimum browser versions remain unresolved. Web Component engine coverage is not a universal React browser-support guarantee.
- **Component catalog:** React chart root exports include additional families beyond the four examples in L2-021; all platform inventories must use actual exports, not old roadmap dates. Detailed semantics for those other chart families, v8 controls, and other v9/Web Component controls remain outside the inspected behavior coverage.
- **Security review:** Review actual library-owned trust boundaries for OWASP relevance before extending security acceptance tests. Authentication/session controls and server-side authorization belong to hosts; universal HTML sanitization is not inferred. Expand structured-input validation requirements for each newly inspected parser or schema.
