# L1 - High-Level Requirements

**Status:** Repository-wide L1 scope confirmed by the user on 2026-10-03; elaborated in [L2.md](L2.md).
**Baseline:** Repository commit `6fdc7bd448`, inspected on 2026-10-03.

## Scope and interpretation

This specification reverse engineers the repository-level contract of Fluent UI Web: React v9 components and foundations, Web Components, charting, legacy React v8 maintenance, and the tooling that validates and releases these libraries. It is an initial capability baseline, not an exhaustive specification of every component or proof that every requirement is satisfied.

Requirements labeled **Documented** are derived from repository documentation; **Observed** requirements also have representative source or test evidence. **Prescribed** requirements come from the authoritative agent instructions. **Proposed** requirements apply the requirements-engineer quality defaults where an existing contract has not been established. A source link establishes provenance, not complete test coverage.

The supplied [agent instructions](../../AGENTS.md) take precedence over conflicting legacy code and documentation. Consumer applications own their business workflows, authentication, authorization, persistence, and deployment. This baseline must not invent application services for a component library or treat old roadmap dates as delivered functionality.

## L1-001: Reusable React user interface controls

Fluent UI must provide reusable React v9 controls and supporting utilities for building applications, with documented public properties and predictable rendering and interaction behavior.

**Basis:** Documented and observed. [Suite README](../../packages/react-components/react-components/README.md), [Button state and defaults](../../packages/react-components/react-button/library/src/components/Button/useButton.ts), [Button interaction tests](../../packages/react-components/react-button/library/src/components/Button/Button.test.tsx).

## L1-002: Consumer customization and composition

React v9 components must support customization through their documented slots, properties, refs, and class names while preserving the component's documented behavior. Components offering controlled and uncontrolled state must honor the respective state ownership contracts.

**Basis:** Documented and prescribed. [Component patterns](../architecture/component-patterns.md), [testing guide](../workflows/testing.md), [controlled menu example](../../packages/react-components/react-menu/stories/src/Menu/MenuControlledCheckboxItems.stories.tsx).

## L1-003: Consistent and customizable themes

Fluent UI must provide theme-based visual styling that supports the documented light, dark, and high contrast themes. React v9 consumers must be able to apply and inherit themes through providers, including supported portal content, and new styling must use the prescribed design tokens.

**Basis:** Documented, observed, and prescribed. [Design tokens](../architecture/design-tokens.md), [provider state](../../packages/react-components/react-provider/library/src/components/FluentProvider/useFluentProvider.ts), [Web Components theming](../../packages/web-components/README.md).

## L1-004: Accessible interaction

Fluent UI controls must implement the accessibility behavior documented for each component, including semantics, keyboard interaction, focus behavior, disabled states, and applicable high contrast and reduced motion behavior. Documentation must identify consumer responsibilities for preserving accessibility during customization.

**Basis:** Documented and observed. [Accessibility guidance](../architecture/component-patterns.md#accessibility-patterns), [Button accessibility and disabled-state tests](../../packages/react-components/react-button/library/src/components/Button/Button.test.tsx), [chart accessibility guidance](../../packages/charts/react-charts/library/README.md#accessibility).

## L1-005: Direction and document context

React v9 components must respect their supported provider context for text direction and target document, including nested providers. Browser-dependent component behavior must use that context so applications can host supported controls in a document other than the default document.

**Basis:** Observed and prescribed. [Provider context handling](../../packages/react-components/react-provider/library/src/components/FluentProvider/useFluentProvider.ts), [agent instructions](../../AGENTS.md).

## L1-006: Server rendering compatibility

React v9 components must support server rendering without unguarded access to browser globals. Web Components must expose their documented declarative rendering and hydration assets, and generated templates and stylesheets must remain consistent with their sources or explicitly documented intentional deviations.

**Basis:** Documented and prescribed. [SSR testing guide](../workflows/testing.md#ssr-safety), [agent instructions](../../AGENTS.md), [Web Components SSR asset workflow](../../packages/web-components/README.md#ssr-templates-and-stylesheets).

## L1-007: Framework-independent Web Components

Fluent UI must provide Web Components that consumers can register individually or collectively through documented entry points, configure through supported APIs, and style through themes. Distribution must include the documented custom elements manifest and declarative component assets.

**Basis:** Documented. [Web Components installation and usage](../../packages/web-components/README.md), [distribution exports](../../packages/web-components/package.json).

## L1-008: Interactive data visualization

Fluent UI charting packages must provide their implemented and exported chart types with documented data inputs, customization, interaction, and accessibility behavior for the corresponding platform. Platform availability must be explicit rather than inferred from another platform's chart catalog.

**Basis:** Documented. [React charts overview](../../packages/charts/react-charts/library/README.md). Historical roadmap dates and planned chart types are not acceptance evidence; the L2 inventory must verify actual exports and tests.

## L1-009: Compatibility and gradual migration

Fluent UI must maintain documented compatibility with supported React versions and enable documented coexistence of v8 and v9 during gradual migration. React v8 must remain within its maintenance scope, and new v9 work must follow the current v9 contract.

**Basis:** Documented and prescribed. [Repository overview](../../README.md), [cross-React testing](../workflows/testing.md), [agent instructions](../../AGENTS.md).

## L1-010: Usable and verifiable package distributions

Published packages must expose documented entry points, public APIs, and applicable type declarations and assets that consumers can resolve from the shipped distribution. Public API changes must update their API documentation and conform to repository compatibility rules.

**Basis:** Documented. [Contribution checklist](../workflows/contributing.md#pr-checklist), [Web Components exports and shipped files](../../packages/web-components/package.json), [bundle isolation verification of built output](../../tools/verify-bundle-isolation/README.md).

## L1-011: Efficient delivery and measurable performance

Fluent UI must provide mechanisms to measure bundle size and rendering performance for configured scenarios. Packages with bundle isolation policies must detect forbidden retained dependencies, identify their origin, and distinguish permitted tracked debt from a clean result.

**Basis:** Observed configuration and documented tooling. [Nx task configuration](../../nx.json), [bundle isolation contract](../../tools/verify-bundle-isolation/README.md). Numeric runtime, throughput, and bundle budgets remain unspecified in this draft; L2 must use verified repository thresholds or separately approved targets.

## L1-012: Maintainable component architecture

New and modified React v9 components must follow the prescribed component structure, typing, styling, ref forwarding, and browser-access rules. Component packages must share cross-cutting functionality through the permitted foundation layers without introducing dependencies on sibling component packages.

**Basis:** Prescribed. [Agent instructions](../../AGENTS.md), [component patterns](../architecture/component-patterns.md), [dependency layers](../architecture/layers.md).

## L1-013: Repeatable validation and release traceability

The repository must provide repeatable project validation through Nx, including the applicable unit, conformance, type, lint, visual, integration, SSR, and compatibility checks. Published package changes must have the required beachball change records and public API documentation updates.

**Basis:** Documented and prescribed. [Testing guide](../workflows/testing.md), [contribution checklist](../workflows/contributing.md), [Nx configuration](../../nx.json), [agent instructions](../../AGENTS.md).

## L1-014: Developer guidance and actionable diagnostics

Fluent UI must provide installation guidance, usage examples, and component-specific API and accessibility documentation. Validation tools must expose failures with enough context to identify the affected package, fixture, or behavior; applicable development warnings must explain configuration problems.

**Basis:** Documented and observed. [Suite usage](../../packages/react-components/react-components/README.md), [component documentation conventions](../architecture/component-patterns.md), [provider theme warning](../../packages/react-components/react-provider/library/src/components/FluentProvider/useFluentProvider.ts), [bundle isolation reports](../../tools/verify-bundle-isolation/README.md).

## L1-015: Security and consumer data boundaries

Fluent UI must provide a documented private vulnerability-reporting route. As a proposed library security contract, controls must preserve safe text rendering, validate library-owned structured inputs at their trust boundaries, and avoid unauthorized transmission or persistence of consumer data. Consumer-owned authentication and authorization must remain enforceable by the host application; disabling or hiding a control must not be documented as an authorization mechanism.

**Basis:** Documented for reporting; proposed for the broader security contract. [Security policy](../../SECURITY.md). OWASP concerns must be assessed against actual library capabilities during L2 elaboration; no login service, session store, or universal HTML/URL sanitizer is inferred from this repository.

## L1-016: Behavior across viewport sizes

As a proposed responsiveness contract, UI controls must preserve their documented interactions and accessibility across extra small, small, medium, large, and extra large host viewports. Layout, overflow, popup positioning, and chart resizing requirements must be specific to each component's sizing contract and leave application layout decisions with the consumer.

**Basis:** Proposed from the requirements-engineer defaults; comprehensive viewport coverage has not been established. L2 must define fixtures at widths below 576px, 576px, 768px, 992px, and 1200px and the expected behavior for each applicable component family.

## Detailed specification and future changes

The [detailed specification](L2.md) contains the acceptance criteria, evidence catalog, and traceability matrix. Future updates must preserve existing requirement IDs, keep each L2 linked to exactly one L1, and retain Given/When/Then criteria. Every confirmed L1 must have at least one L2; detailed coverage must not be claimed for component families not yet inspected.

Acceptance tests added during subsequent development must include a comment header identifying the L2 IDs they cover, for example `// Traces to: L2-001, L2-003`. Existing tests are evidence to map to L2, not proof that the original code followed ATDD. New implementation work must follow the skill's requirement-to-failing-test-to-implementation sequence.
